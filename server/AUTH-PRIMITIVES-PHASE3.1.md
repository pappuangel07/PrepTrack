# PrepTrack Phase 3.1 — authentication primitives

This phase adds reusable authentication primitives and schema version 3, but does not add authentication endpoints, registration, or owner bootstrap. Session middleware is not wired into `server/server.js`; later integration must mount `createSessionProvenanceMiddleware(store)` immediately after `express-session` and configure Express proxy trust narrowly.

## Runtime and dependencies

The implementation was checked on Node.js 24.14.0 with `better-sqlite3` 13.0.3 and SQLite 3.53.4. `argon2` 0.45.2 declares Node.js `>=16.17.0`; a native Argon2id hash/verify smoke test is part of this phase. `express-session` 1.19.0 is used as the Store base. The primitives require schema version 3, including `session_revocations`; no migration runs automatically at server startup.

## Password handling

`auth/passwords.js` uses Argon2id with explicit parameters (19 MiB memory, two iterations, one lane, 32-byte output). New passwords require at least 12 Unicode code points and at most 1,024 UTF-8 bytes. Verification applies the same 1,024-byte ceiling. Encoded hashes are generated by the library. Invalid stored hashes fail verification without exposing parser details.

## Sessions and cookies

`SQLiteSessionStore` stores Express session JSON in `sessions` and revocation hashes in `session_revocations`. Expiry is bounded by a 30-minute idle timeout and a seven-day absolute lifetime. Tombstones remain until the session's absolute expiry plus 24 hours. `get`, `set`, `touch`, `destroy`, and `cleanupExpired` use `BEGIN IMMEDIATE`; an operation that removes an expired session first commits its tombstone in the same transaction. Late saves cannot create a missing row: new sessions require request-local, SID-bound provenance; loaded sessions carry separate `loaded` provenance; missing rows without a valid new-session proof are rejected. The provenance is kept in a module-private `WeakMap`, not in user-visible session data. Times are evaluated after the transaction obtains its write lock. SQLite can still return busy errors under external lock contention; integration must retain a finite busy timeout and handle store errors.

The options factory requires an explicit app origin and a session secret of at least 32 bytes. Production requires HTTPS and uses a host-only `__Host-` cookie (`Secure`, `HttpOnly`, `SameSite=Lax`, path `/`, no Domain). Local development permits HTTP only on localhost/loopback and uses a non-prefixed host-only cookie with `Secure=false`. The `proxy` option is omitted so `express-session` uses Express's `req.secure`. When deployed behind a reverse proxy, configure Express `trust proxy` only for the exact proxy address/CIDR or known hop count; never use `true` on an Internet-facing app. TLS must be enforced at the edge. A trusted-proxy cookie test exercises `express-session@1.19.0`; the production server itself is not wired in this phase.

The installed `express-session@1.19.0` lifecycle was inspected and tested: its middleware replaces `store.generate`, invokes configured `genid`, calls `createSession` when loading/reloading, invokes `destroy` then `generate` during regeneration, and calls `set` or `touch` when saving a response. The store binds generated provenance in a post-session middleware and binds loaded provenance through the installed `createSession` hook. Regeneration is overridden by the store to bind the new SID immediately. Tests exercise these hooks against the installed version. Login integration must regenerate the session ID before attaching `studentId`, and logout must destroy the server-side row and clear the cookie using the same name/options. Regeneration must not copy pre-authentication session data other than explicitly approved state.

## CSRF and student guard

`csrf.js` issues a random 256-bit synchronizer token stored in the session. Unsafe methods require both an exact configured Origin and a matching `X-CSRF-Token`; comparisons use constant-time equality. Safe methods are GET, HEAD, and OPTIONS and must remain free of state changes in route handlers. The configured Origin must be derived from deployment configuration, never from an incoming request header.

`require-student.js` reads a positive safe integer only from server-side `req.session.studentId`, then exposes a frozen `req.student.id`. Route handlers must use that ID in every ownership-scoped SQL predicate; this helper does not itself authorize resource ownership.

## Persistent rate limiting

`PersistentRateLimiter` uses the existing `auth_rate_limits` table and an application secret to HMAC the normalized scope/dimension/identifier. Raw emails and IP addresses are never stored, and separate scopes receive unrelated hashes. Email normalization trims and lowercases; other identifiers trim only, so the integrating HTTP layer must canonicalize IP addresses consistently. `consume` uses an immediate transaction and samples time after obtaining the writer lock. Policies must use a positive safe-integer limit no greater than the schema's 1,000,000 attempt ceiling; derived expiry timestamps must also remain safe integers. Expired rows can be pruned in bounded batches with `cleanup`; active blocks are retained.

## Tests and deployment requirements

Auth primitive tests use isolated temporary databases with a disposable copy of the v3 table definitions. Migration tests use fresh disposable baselines and disposable copies. They never migrate the live PrepTrack database. Later integration must add route-level tests for cookie clearing, actual production proxy configuration, Origin configuration, ownership predicates, and response behavior under SQLite lock contention.

Before public launch, email verification and secure password recovery remain required features. They are intentionally outside Phase 3.1. The application must also deploy over HTTPS, protect session/HMAC secrets, and operate a tested backup/restore process.
